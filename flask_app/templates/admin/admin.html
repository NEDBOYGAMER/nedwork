Guide: gate one app function behind its own permission (the colors_ai pattern)

How permissions work here (living doc - kept up to date as the console changes):

  1. Keys are created HERE (Permissions tab). A key has a name, a description and a kind:
    • Access key - gates opening an app. Assigned in the Apps tab under "Requires to open"; the app then needs it (any-of next to the app's other access keys). tierforge is the example: hold it and TierForge opens.
    • Function key - gates one feature inside an app, never the app itself. Shown in the Apps tab under "Functions" (colors_ai is the example). The feature's own code enforces it; the link is documentation for this console. A function key can never lock anyone out of an app - the server filters it out of the open requirement by design.
  2. Keys get assigned in the Apps tab. One card per app: title, link, types, description, tile image (drag & drop - saved to img/apps/ and linked automatically), "Requires to open" chips (access keys) and "Functions" chips (function keys). The kinds are strictly separated: an access key cannot become a Functions chip and vice versa.
  3. Keys get granted in the Users/Groups tabs. "+ key" chips on a person or group. Without a grantee a key simply switches its gate off for everyone.
  4. Backend enforcement (code, one decorator per key): 
    @permission_required("core", REDIRECT)
@permission_required("colors_ai", REDIRECT)
def palette_from_image(user):
    ...
    Decorators stack like AND - every key must be held. Keep the app's general keys (core) on their own decorator. Use API mode when the JS should receive a clean JSON 403 instead of a redirect.
  5. Frontend concealment. The server is the real gate, but users should not see controls they can never use. GET /auth/api/who returns the logged-in user's held keys (top-level permissions list): 
    const who = await fetch('/auth/api/who', {credentials:'same-origin'})
    .then(r => r.ok ? r.json() : null);
const canUse = !!who && who.permissions.includes('colors_ai');
document.getElementById('upload-btn').style.display =
    canUse ? '' : 'none';
  6. App links are enforced - handle with care. "Permits" on a key row lists the apps whose OPEN requirement contains the key (any-of!). A key with several app chips opens ALL of them for its holders. Removing a chip is the safe direction; adding one weakens the app's lock for key holders.
  7. Naming. Access keys: the app's name (tierforge) or domain (files.read). Function keys: <app>_<function> (colors_ai, tierforge_export, trivia_host). Stay consistent per app.
